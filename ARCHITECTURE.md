# Geophysical Acquisition Module Firmware Architecture

## Purpose

This document defines where firmware responsibilities belong, how modules may
depend on each other, and where new code should be added. Its purpose is to keep
the repository predictable as the product grows and to prevent hardware wiring,
component logic, protocol logic, and application behavior from becoming mixed.

The document describes the intended architecture. A directory or file may exist
before its interface or implementation is complete; see the implementation
status table at the end of this document.

## Design principles

- Component drivers remain independent of ESP-IDF, board wiring, FreeRTOS,
  storage, and communication transports.
- The ESP32-S3 DevKit is an immutable compute platform. Custom PCB behavior and
  wiring belong to the selected board revision.
- Product behavior belongs to the application layer, not to component drivers or
  platform adapters.
- UART, USB, Bluetooth, and future links carry the same transport-independent
  protocol.
- Stateful hardware resources have one owner during normal operation.
- Interrupt handlers do the minimum work necessary and wake the owning task.
- Hardware starts in a safe state and startup stops safely when a required
  subsystem cannot be initialized.
- External dependencies are pinned and are not modified locally.
- Generated files and local tool state are not committed.

## Where new code belongs

| New code | Location |
|---|---|
| Portable status categories or other truly cross-layer firmware types | `firmware/common/` |
| Product mode, recording behavior, or acquisition policy | `firmware/app/` |
| FreeRTOS task and its owned queues or buffers | `firmware/app/` |
| Rev-1 GPIO, chip select, polarity, or peripheral assignment | `firmware/boards/rev_1/` |
| Behavior specific to a removable analog card | `firmware/analog_cards/<card>/` |
| Magnetic-card SET/RESET pulse sequence, width, dead time, and settling policy | `firmware/analog_cards/magnetic/` |
| Rev-1 18 V rail control and physical SET/RESET shift-register mapping | `firmware/boards/rev_1/` |
| Register map or datasheet behavior for one IC | `firmware/drivers/<component>/` |
| ESP-IDF SPI, I2C, UART, GPIO, timer, or SDMMC adapter | `firmware/platform/esp32s3_devkit/` |
| Message framing or serialization | `firmware/protocol/` |
| USB, UART, or Bluetooth byte movement | `firmware/transports/` |
| Wire-format contract shared with the host | `shared/protocol/` |
| Host-only behavior | `version_2/host_app/` |
| PCB or electrical design | `version_2/hardware/` |

When a change seems to fit in more than one location, place the hardware-neutral
policy at the higher layer and the hardware-specific mechanism at the lower
layer. For example, the application decides when recording starts, the storage
task owns the filesystem, the board keeps the Rev-1 SD mux in its fixed ESP32
state, and the platform performs the SDMMC operations. Likewise, the magnetic
card module defines how a magnetic SET/RESET pulse is generated, while the
Rev-1 board implements the mainboard's 18 V rail control and physical SH2 output
mapping used by that sequence.

## Dependency direction

```text
app_main
├── platform
├── board
└── application
    ├── acquisition / processing / storage
    └── communication task
        ├── protocol
        └── transport interface
            ├── UART transport
            ├── USB transport
            └── Bluetooth transport

board
├── analog-card integrations
├── component drivers
└── platform services

analog-card integrations
└── component drivers

transports
└── platform services

platform
└── ESP-IDF / FreeRTOS
```

Allowed dependencies:

- All firmware layers may use the portable types in `common/`; `common/` does
  not depend on any other firmware component, ESP-IDF, or FreeRTOS.
- `main/` initializes the platform, selected board revision, and application.
- `app/` uses application types, board-level services, protocol interfaces, and
  transport-independent communication interfaces.
- `boards/` uses analog-card modules, component drivers, and platform services.
- `analog_cards/` uses portable component interfaces and describes card-level
  topology or sequencing without knowing ESP32 GPIO numbers.
- `protocol/` uses portable C types and algorithms only.
- `transports/` use their corresponding platform or third-party service and do
  not interpret application messages.
- `drivers/` use portable callbacks and opaque contexts supplied during
  initialization.
- `platform/esp32s3_devkit/` uses ESP-IDF and FreeRTOS APIs.

Forbidden dependencies:

- Component drivers must not include ESP-IDF, board, application, protocol, or
  FreeRTOS headers.
- Platform code must not know that an AD7779, LSM6DSV, MAX-M10S, analog card, or
  other product component uses a peripheral.
- Analog-card modules must not contain ESP32 GPIO numbers or call ESP-IDF APIs.
- Protocol framing and message encoding must not call UART, USB, or Bluetooth
  implementations directly.
- Transports must not decode product commands or manipulate sensors.
- Application tasks must not manipulate component registers or ESP32 GPIO
  registers directly.
- Third-party source code must not be edited to add product behavior.

## Firmware entry point

`version_2/firmware/main/main.c` is the composition root. It provides ESP-IDF's
`app_main()` and is limited to:

1. Initialize required platform services.
2. Initialize the selected custom board revision.
3. Place the board in its defined safe initial state.
4. Initialize application resources.
5. Create application tasks, queues, and synchronization objects.
6. Enter a safe and diagnosable failure state if startup cannot complete.

ESP-IDF starts the FreeRTOS scheduler before it calls `app_main()`. The firmware
must not call `vTaskStartScheduler()`. `app_main()` may return after creating the
long-lived application tasks.

Product algorithms, peripheral register configuration, packet parsing, and
long-running acquisition loops do not belong in `main.c`.

## Application layer

The application layer decides what the acquisition module does. It works with
timestamped samples, recordings, configuration, commands, product state, and
diagnostics through board-level and protocol-level interfaces.

### `app.c` and `app.h`

These files coordinate application startup. They create application-owned
queues, buffers, synchronization objects, and tasks. They do not accumulate all
product behavior into one large loop.

### Application types

Types exchanged between application modules should eventually be collected in
`app_types.h` or smaller domain headers. Examples include:

- Timestamped ADC and IMU samples.
- GNSS time and position fixes.
- Recording and acquisition requests.
- Application modes and subsystem health.
- Configuration values expressed in physical units.

Application types must not contain:

- ESP-IDF handles or register definitions.
- Board GPIO or peripheral assignments.
- Component register values.
- Raw on-wire protocol structures.
- FreeRTOS internal implementation structures.

## FreeRTOS task ownership

One task owns each stateful resource during normal operation. Other tasks
communicate with the owner through queues, task notifications, stream buffers,
or explicit request interfaces.

| Task | Intended responsibility | Current status |
|---|---|---|
| `task_acquisition` | Configure acquisition devices, wait for data-ready events, read samples or FIFOs, and timestamp data | Scaffolded |
| `task_processing` | Calibration, filtering, derived channels, and event processing when workload justifies a separate task | Provisional scaffold |
| `task_storage` | Own filesystem operations, recordings, buffered writes, flushes, and storage faults | Scaffolded |
| `task_communication` | Decode protocol messages, dispatch commands, and encode responses | Scaffolded |
| `task_bluetooth` | Manage Bluetooth connection state and asynchronous radio events without duplicating protocol behavior | Provisional scaffold |

`task_processing` should remain an ordinary application module unless its CPU
time, latency, or buffering requirements justify an independent task.

`task_bluetooth` should remain separate only if the Bluetooth stack or connection
management requires an asynchronous state machine. UART, USB, and Bluetooth
must not each implement their own command protocol.

Interrupt handlers acknowledge the event, capture essential state when needed,
and notify the owning task. They do not parse messages, perform long bus
transactions, write files, or run product algorithms.

## Custom board integration

### `board_config.h`

`boards/rev_1/board_config.h` is the authoritative firmware mapping for the
modifiable Rev-1 carrier PCB. It contains:

- ESP32 GPIO assignments and signal polarities.
- SPI, I2C, UART, and SDMMC controller selection.
- Chip-select, reset, enable, interrupt, and data-ready assignments.
- Power-rail and source-presence controls.
- SD/USB multiplexer control signals.
- Analog-card detect and control assignments.
- Bus limits, timing limits, and board-level timeouts.

It must not contain product algorithms, component register tables, protocol
definitions, or long executable procedures.

### `board.c` and `board.h`

`board.c` initializes the custom PCB and connects portable drivers to platform
services. For example, it associates an AD7779 instance with the selected SPI
service, chip-select signal, reset signal, data-ready interrupt, and timing
callbacks.

`board.h` exposes board-level services to the application without leaking
ESP-IDF handles, GPIO numbers, or component register details. If `board.c`
becomes too large, it may be divided by resource while `board.h` remains the
public application-facing interface.

Safe output levels must be established before a peripheral or task can use the
board. Power enables, sensor set/reset controls, the shift-register output
enable, ADC control signals, and the SD/USB multiplexer require explicit startup
states derived from the schematic and component datasheets.

## ESP32-S3 DevKit platform

`platform/esp32s3_devkit/` represents the immutable ESP32-S3 DevKit compute
platform and its ESP-IDF integration. The name intentionally distinguishes the
fixed DevKit from the custom, modifiable carrier PCB in `boards/rev_1/`.

The platform layer is responsible for mechanisms such as:

- ESP-IDF system, clock, and power initialization that the application must
  explicitly control.
- GPIO, SPI, I2C, UART, SDMMC, USB, DMA, timer, and interrupt operations.
- Monotonic time, delays, and critical sections.
- ESP-IDF and FreeRTOS error translation.
- DevKit-intrinsic resources and immutable constraints.
- Build integration and optional custom partition, linker, or startup support.

Platform interfaces describe MCU and DevKit services. They do not describe
which product sensor uses those services. Carrier-board GPIO mappings and
product component instances remain in `boards/rev_1/`.

ESP-IDF normally supplies startup code, the linker layout, and the FreeRTOS port.
The local `startup/` and `linker/` directories should remain empty unless a
documented product requirement needs to override an ESP-IDF default.

## Analog-card integration

`analog_cards/` describes removable or selectable card assemblies rather than a
single integrated circuit. An analog-card module may know:

- Which portable component drivers make up that card.
- Card-level channel ordering and supported measurements.
- Required set/reset or excitation sequences.
- Card-level timing and settling requirements.
- Detection and identification rules.
- Card-specific health and availability states.

An analog-card module must not know ESP32 GPIO numbers, ESP-IDF peripheral
handles, protocol packet layouts, filesystem behavior, or user-interface policy.
The selected `board` supplies its control and bus callbacks.

`analog_cards/magnetic/` owns the complete magnetic SET/RESET behavior: allowed
operations, pulse width, ordering, dead time, and post-pulse settling policy. It
uses callbacks supplied at initialization and never knows the 18 V enable bit or
the SET/RESET shift-register positions. The Rev-1 board owns those mainboard
mechanisms and remains the only writer of the physical 74HC595 chain.

`analog_cards/acc_geoph/` has no SET/RESET pulse behavior. Card-specific gain
control for that card belongs in its own module and is independent of the
magnetic pulse interface.

Current card scaffolds are:

- `analog_cards/magnetic/` for the magnetic acquisition card.
- `analog_cards/acc_geoph/` for the geophysical accelerometer card.
- `analog_cards/card_detect.*` for common card-presence handling.

## Component drivers

Each driver describes one physical component according to its datasheet.

Typical files are:

```text
component.c          Public behavior and datasheet logic
component.h          Public portable interface
component_reg.h      Private register and bit definitions, when applicable
```

Current component drivers are:

- `ad7779`: eight-channel ADC control, status, and sample-frame handling.
- `lsm6dsv`: accelerometer and gyroscope configuration and sample handling.
- `max_m10s`: GNSS configuration and message handling.
- `74hc_hct595`: serial-to-parallel output control.

A component driver may know:

- Supported modes, ranges, data rates, and frequencies.
- Register addresses, commands, and bit fields.
- Component-specific SPI, I2C, or UART transaction formats.
- FIFO and raw sample layout.
- Conversion from raw values to documented units.
- Component identity and component-level error conditions.

A component driver must not know:

- Which ESP32 peripheral or GPIO is used.
- How ESP-IDF performs a transfer.
- Which custom board revision is active.
- Which FreeRTOS task called it.
- Whether data will be stored, processed, or transmitted.

The board supplies portable communication, GPIO, delay, and time callbacks plus
an opaque context to each driver instance. Unsupported functionality is omitted
or returns an explicit not-supported result; it is not declared without an
implementation.

## Storage and fixed SD-card ownership

The storage architecture crosses several layers:

- `task_storage` owns normal filesystem access and recording files.
- `board` initializes the product-specific SD/USB multiplexer once for ESP32
  ownership and holds the USB2641 reset/isolated.
- `platform` performs ESP-IDF SDMMC and filesystem operations.

When milestone-2 storage is implemented, the firmware must model at least these
storage states:

- Unavailable or uninitialized.
- Owned by the ESP32 for recording or playback.
- Faulted or unexpectedly removed.

V2 Rev-1 firmware does not expose the SD card through the USB2641 and does not
switch SD ownership at runtime. The exact fixed mux select/enable levels and
USB2641 reset state belong to the Rev-1 board implementation and must be
verified against the schematic and datasheets.

## Communication architecture

UART, USB, Bluetooth, and future transports carry one application protocol.

```text
Host application
├── USB connection ──────────┐
├── UART connection ─────────┤
└── Bluetooth connection ────┤
                             v
                    Firmware protocol
                             v
                    Application commands
```

### Protocol

`firmware/protocol/` is independent of physical transports:

- `protocol_frame` detects frame boundaries and checks framing integrity.
- `protocol_messages` serializes and deserializes typed command and data
  payloads.
- Protocol state eventually manages versions, sequence numbers, requests,
  acknowledgements, and responses.

Parsing accepts partial input and multiple frames in one buffer. It must not
depend on USB packet boundaries, UART read sizes, or Bluetooth packet sizes.

Raw C structures are never transmitted directly. Fields are serialized
explicitly using fixed widths and a specified byte order.

### Transports

`transports/transport.h` defines the common byte-transport contract. UART, USB,
and future Bluetooth implementations independently manage connection state,
partial transfers, buffering, and backpressure. They do not interpret product
commands.

Debug text must never be inserted into the binary protocol stream. Logging uses
a dedicated debug channel or an explicitly separate framing/channel mechanism.

### Shared specification

`shared/protocol/` is the contract between firmware and the host application. It
contains or will contain:

- Protocol version and compatibility rules.
- Frame and message layouts.
- Message identifiers and stable status codes.
- Byte order and checksum/CRC definitions.
- Units, scaling, and invalid-value representations.
- Valid and invalid test vectors.
- Recording transfer, interruption, and resume behavior.

The firmware and host application implement this specification independently
and are tested against the same vectors.

## Time and data conventions

- Application-facing measurements use documented physical units.
- Units appear in field names or API documentation.
- Fixed-width integer types are used where binary representation matters.
- Protocol and stored-data layouts are serialized explicitly.
- Monotonic acquisition time and GNSS/UTC time are separate clock domains.
- Every timestamp type identifies its unit, epoch, and clock domain.
- Mapping GNSS time to acquisition time is explicit and includes validity and
  uncertainty when available.
- Driver-specific types do not leak into processing, storage, or protocol layers
  unless that dependency is intentional and documented.
- Mutable global state is avoided. Shared state has one owner and explicit
  synchronization.
- Dynamic allocation after application startup is avoided unless a bounded and
  reviewed use case requires it.

## Error handling

Each layer translates errors at its boundary:

- Platform errors describe ESP-IDF, peripheral, timing, or MCU failures.
- Driver errors describe component failures or invalid component parameters.
- Analog-card errors describe card detection, identification, sequencing, or
  availability failures.
- Board errors identify unavailable or incorrectly initialized resources.
- Application errors describe product operations such as acquisition or
  recording failures.
- Protocol responses expose stable host-visible status codes.

ESP-IDF error values, low-level bus errors, and private driver status values must
not be transmitted directly as the public protocol.

Fatal startup failures place the hardware in a safe and diagnosable state rather
than continuing with partially initialized resources.

## Initialization order

The intended ESP-IDF startup sequence is:

```text
ESP32-S3 reset
    v
ESP-IDF bootloader and system initialization
    v
FreeRTOS scheduler and ESP-IDF main task
    v
app_main
    v
required platform services
    v
selected board revision and safe outputs
    v
component and analog-card instances
    v
application queues, buffers, and tasks
    v
normal operation
```

Tasks must not access a resource until its platform, board, and driver
initialization has completed successfully. Optional devices may be marked
unavailable when product requirements permit degraded operation; required-device
failures prevent acquisition from starting.

## Build and dependency conventions

- `version_2/firmware/CMakeLists.txt` is the ESP-IDF project entry point.
- `version_2/firmware/main/` is the ESP-IDF main component.
- Other architectural directories are registered as ESP-IDF components or
  component search paths without changing their ownership boundaries.
- Reproducible defaults belong in `sdkconfig.defaults`; developer-generated
  `sdkconfig` files remain local unless a deliberate decision says otherwise.
- ESP-IDF Component Manager dependencies use `idf_component.yml` and a committed
  dependency lockfile when applicable.
- `build/`, `managed_components/`, generated binaries, and IDE state are ignored.
- Vendor datasheet PDFs in `version_2/docs/datasheets/` remain local; their
  source links are tracked instead.
- Warnings should be enabled broadly and treated as errors in automated builds
  once the initial platform scaffold is stable.

## Verification strategy

- Portable drivers are unit-tested on the host with fake bus, GPIO, delay, and
  time callbacks.
- Protocol encoding and parsing are tested against shared golden vectors,
  malformed data, partial frames, and multiple frames per input buffer.
- Board and platform services receive hardware smoke tests for each peripheral.
- Acquisition tests cover data-ready timing, buffering, overruns, and sustained
  throughput.
- Storage tests cover full media, removal, write errors, fixed mux isolation,
  unmounting, and interrupted power.
- Long-duration tests cover timestamp drift, GNSS loss/reacquisition, queue
  pressure, and watchdog recovery.
